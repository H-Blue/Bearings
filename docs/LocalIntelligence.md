# Bearings local intelligence

Implementation reference, October 11, 2026. This document describes the current source; executed checks and remaining verification are recorded in [Testing.md](Testing.md). The approved scope is [BEARINGS_AI_IMPLEMENTATION.md](BEARINGS_AI_IMPLEMENTATION.md). Older documents describing AI as future work describe the earlier journaling foundation.

## Components and boundaries

| Component | Responsibility |
| --- | --- |
| `JournalStore` | Fresh committed reads, isolated journal/derived writes, explicit saves, invalidation and fingerprint checks. |
| `JournalEntrySnapshot` / `LocalJournalRetrieving` | Immutable journal values passed into local analysis. |
| `JournalIntelligence` | Replaceable asynchronous provider interface with availability, daily analysis, staged weekly extraction/composition, monthly reflection and editor Emotional Zoom operations. |
| `AppleJournalIntelligence` | Apple on-device availability checks, trusted instructions, fresh sessions and guided output. |
| `JournalAnalysisEngine` | Serial inference, complete source segmentation, adaptive context retries, grounded weekly signal validation and hierarchical combination. |
| `JournalAnalysisService` | Observable availability/results, cache reuse, task coordination, cancellation and completion triggers. |
| `AnalysisTypes` / `AnalysisRecords` | Framework-independent values, civil periods, fingerprints and separate SwiftData derived records. |
| `DailyReflectionSection` / `ReflectionView` / `EmotionPalette` | Daily and period results, correction/retry controls and accessible timeline indicators. |
| `JournalEditorView` | A user-triggered, transient Emotional Zoom over the current draft; the result is discarded when the draft changes. After a committed change, it separately invokes the local safety boundary. |
| `JournalSafetyCheckService` / `ConservativeJournalSafetyEvaluator` | A Foundation Models-independent, injectable check for a small reviewed set of explicit current first-person intent phrases. |
| `TrustedContactStore` / `TrustedContactPinging` | Isolated local contact persistence and an injectable future transport boundary. The shipping transport cannot send. |

Original journal writing remains authoritative. Summaries and emotion suggestions are interpretations, stored separately and labeled in the interface. The broader assistant, book retrieval, cloud inference, sync and progressive design reveal are outside this milestone.

## Journal metadata and additive storage

`JournalEntry` retains its existing UUID, `body`, `periodRawValue`, `createdAt`, `modifiedAt` and Gregorian civil `dayKey`. It adds optional `createdTimeZoneIdentifier`. New entries receive the current creation zone; existing entries retain `nil` because their original zone is unknown. Creation time and creation zone are preserved during edits and moves. `modifiedAt` advances on body, period or day changes, with a nondecreasing policy if the device clock moves backward. Unchanged saves do not alter it.

The selected day describes the experience rather than the saving instant. A backdated entry can be created today, retain today's exact creation timestamp and zone, and belong to yesterday's `dayKey`. Travel never reinterprets that key. The editor maintains a separate selected-day draft and explicitly saves it with the writing and period.

The SwiftData schema contains `JournalEntry`, `DailyAnalysisRecord`, `ReflectionRecord`, `EmotionOverrideRecord` and `TrustedContact`. Trusted contacts are a separate table and never become analysis input. Daily records have a unique day key; period records have a unique kind/start/end key. They store validated Codable content as JSON `Data`, source fingerprints, generation timestamps, analysis versions and stale flags. Corrections are separate records with an emotion and modification timestamp. Removing a day's last entry or regenerating its analysis preserves its correction.

The optional journal addition and new empty tables permit SwiftData's inferred additive migration. No historical timestamp or zone is fabricated. `JournalMigrationTests` writes the frozen pre-AI `JournalEntry` shape into a real file store, then opens it through the current schema and verifies journal identity/content/timestamps, unknown legacy zones, new correction storage and a further reopen. Its executed result belongs in Testing.md.

The bundle identifier, configuration name `ReCollect`, and Application Support `ReCollect/Journal.store` path remain compatibility values. Initialization failures reach the existing visible retry screen; production never substitutes an empty temporary store.

## Optional safety check-in boundary

The safety check-in is an optional local offer. It is not diagnosis, continuous monitoring, prediction, a risk score, guaranteed detection or automatic outreach. It does not use Foundation Models. `JournalSafetyEvaluating` receives only the committed body after the user completes a successful isolated editor save. Draft keystrokes, debounce autosaves, background saves and failed saves do not run it. The initial deterministic evaluator normalizes case and ordinary punctuation, then recognizes a deliberately small reviewed set of explicit current first-person intent statements. It suppresses quoted text and sentences marked as historical, fictional, lyrical, reported or news context. A negative result does not establish safety. An evaluator error leaves the committed journal readable and unchanged.

Signals exist only in root view state long enough to offer the sheet. Bearings stores no matched excerpt, safety event, diagnosis or permanent label. Journal entries, daily analyses, period reflections, emotion overrides and trusted contacts remain separate. Contact names and phone numbers never enter prompts, summaries, fingerprints, analytics or logs.

The check-in states that Bearings may be misunderstanding the writing. Its configurable 15, 30 or 60 second timer controls only the prominent offer and dismisses without action. Reaching the transport requires four deliberate steps: choose Reach out, select exact enabled recipients, review and edit the exact neutral message, then press Send. Every stage retains Not now. Dismissal, timeout, navigation, backgrounding and termination do not call transport. The `PreviewOnlyTrustedContactPinger` used in production always returns “Sending is not available in this build”; it performs no SMS, call, notification or network request. Professional resources are static text and do not silently open another app.

Trusted contacts are entered manually, so Bearings requests no Contacts permission. `TrustedContactStore` uses fresh SwiftData transaction contexts, explicit saves and rollback on failure. Settings shows retryable failures. The model is an additive table in the existing `ReCollect` store, preserving compatibility identities and existing journal data. A visible Settings control and a named accessibility action exist on both timeline and day screens. A predominantly vertical downward drag over 100 points also opens the native Settings sheet; the day gesture is enabled only at the scroll view’s top boundary, while horizontal timeline movement remains available.

## Transaction and cache correctness

Every mutation uses a fresh transaction context with autosave disabled. Journal changes and the invalidation of their dependent daily/weekly/monthly results share one explicit save. Failed saves roll back only that context. Visible entries are mirrored only after a successful commit; independent editor drafts remain available to retry. All store reads use fresh contexts and exclude pending changes, preventing an observed model's unsaved edit or insertion from becoming analysis input.

Entry creation, editing, deletion and reassignment mark affected daily records stale and mark every stored overlapping period stale, including clipped weeks. A move affects both civil days. Correction changes invalidate overlapping reflections while preserving the original AI classification. A change to a day, its derived daily analysis or its correction also invalidates the weekly reflection for the directly following week because that result may contain continuity from the changed week. Saving or regenerating a full weekly reflection invalidates that same direct dependent. Invalidation stops there; the store never walks an unlimited historical chain. Successful journal writes enqueue changed days; derived saves update the UI revision without enqueueing another journal-analysis cycle.

SHA-256 fingerprints use length-prefixed values, source UUIDs, day keys, complete bodies, periods and creation/modification instants, plus the analysis version. A reflection fingerprint also includes the requested period, applicable corrections and current derived inputs. Weekly fingerprints include current daily records and, when valid, the one immediately preceding full-week reflection. Monthly fingerprints include their clipped weekly records. Derived identities cover stored content, source fingerprint, generation time, version and stale state. Fingerprints are cache identities, never logs or exported journal data. This detects content changes even when two edits share the same modification timestamp and prevents a current week from reusing output after its direct historical context changes.

Daily and reflection caches are reused only when the stale flag is clear, the version matches and the current source fingerprint matches. Analysis version 5 marks the staged weekly generation and reporting semantics, so older weekly output is regenerated. Version 4 introduced summary-first daily presentation, and version 3 introduced Sunday–Saturday reporting. Before persisting generated output, `JournalStore` compares the fingerprint again in the isolated transaction. A changed source throws `AnalysisError.sourceChanged`; an old result cannot overwrite current content. Daily coordination makes one bounded retry from the latest committed source. Period failures remain visible and retryable. Malformed selected derived payloads or period metadata are treated as unusable caches: an available model can regenerate and replace only that interpretation through the same source-checked transaction. Fetch errors still propagate. Valid manual corrections load independently of derived records, so damaged interpretations cannot hide a committed choice. Without an available model, corrupt derived bytes remain saved and the read failure stays visible.

## Civil reporting periods

Weeks begin Sunday and end Saturday. On a Sunday, the weekly review targets the completed prior Sunday–Saturday period; during the rest of a week it targets the containing week. Calendar months run from their first through last civil day. `AnalysisPeriod` calculates these boundaries using a Gregorian calendar in UTC civil space; timestamps and the device's current zone do not decide membership. The journal's representable years remain 1–9999. Boundary weeks clamp their date values before conversion back to civil components, preserving the correct era at the earliest supported year.

Daily analysis combines all nonblank committed entries with the same day key. Weekly reflection treats the requested week's complete journal writing and current daily analyses as authoritative evidence. It may add exactly one current, nonstale, same-version reflection for the immediately preceding Sunday–Saturday week, clearly labeled as historical AI context. It never requests or generates that earlier reflection while generating the current one, and current writing explicitly takes priority over prior interpretation. Monthly reflection combines weekly reflections clipped to that month and a separate collection of that month's dated daily facts. For example, a September 27–October 3 week contributes only October 1–3 to October's monthly reflection. A cached full week spanning another month is never substituted for that clipped period.

Weekly generation has two model stages. The first extracts a compact `WeeklySignals` packet: repeated work or focus, dated events, explicit goals, progress, obstacles, unfinished threads, emotional changes and relevant preceding-week continuity. Each bounded source line receives a short local evidence ID. The model selects an ID for every extracted item; the adapter resolves that ID back to the exact source line, and the engine rejects unknown IDs. Dated events must also fall inside the requested period. This avoids accepting a model-paraphrased quote as source evidence while keeping journal text on device. Signals from bounded chunks are deduplicated before the second stage. The second stage sees only that compact packet, not the raw journal transcript. It writes the work focus, week account, progress and unresolved work, what helped, one supported improvement and a lesson-readiness conclusion. Readiness evidence must exactly match an extracted signal statement. If readiness or an improvement is unsupported, the output says evidence is insufficient and provides one open-ended question. The interface presents these concepts under their own headings rather than reusing monthly relationship or interest fields.

Important events are preserved independently from prose combination. Period results use the dated daily event collection rather than accepting a shorter model-produced event list. This preserves extracted facts through the hierarchy; it does not establish that a model extracted every real event correctly. Original journal entries remain available for review.

## Local model support

The app continues targeting iOS 17. `canImport(FoundationModels)` gates the framework at compilation, and an iOS 26 availability check creates the Apple provider only on supported operating systems. Earlier systems receive an unavailable provider while retaining journaling and manual emotion choices. Only `SystemLanguageModel.default` is used. Apple's documentation identifies this model as on-device and requires availability checks and a fallback experience. [Apple: generating content](https://developer.apple.com/documentation/foundationmodels/generating-content-and-performing-tasks-with-foundation-models)

The provider checks device eligibility, disabled Apple Intelligence, a model that is still preparing, other unavailability and the current locale. It rechecks before generation. Useful unavailable messages preserve access to the saved journal; no remote fallback is implemented. The installed Xcode 27 SDK exposes the core APIs from iOS 26, exact token counting from iOS 26.4, and the newer `LanguageModelError` from iOS 27. The source gates each optional API independently and recognizes the older context-window error as well. [Apple: tokenCount](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel/tokencount(for:))

Guided generation uses `@Generable` output structures and an enum containing only the eight supported emotions. Daily instructions request a concise account of what happened first, then only emotions expressed by the writer or strongly supported by the writing. An unsupported emotion is stored as `uncertain`, with no secondary emotion, and the interface omits that uncertain classification from the optional “Notable emotions” list. A manual choice, including mixed/uncertain, remains visible because it is the writer's correction. `@Guide` descriptions request concise, grounded fields. The adapter trims and validates output before use. Emotional Zoom requires any identified vague passage to be an exact excerpt from the submitted draft, a tentative explanation and one non-diagnostic open-ended question. Instructions treat journal material as data, preserve ambiguity, distinguish the writer's emotions from other people's and prohibit invented events or diagnoses. These instructions reduce errors; they do not make semantic accuracy guaranteed. [Apple: guided generation](https://developer.apple.com/documentation/foundationmodels/generating-swift-data-structures-with-guided-generation)

## Context size, scheduling and interruption

Each provider request creates a new session. The engine serializes expensive operations and splits every source entry into Unicode-scalar-safe segments with a 2,400 UTF-8 byte budget. Joined segments reproduce the complete input; byte budgeting is a conservative policy rather than an exact tokenizer count. Weekly extraction gives every bounded segment the requested week bounds, then validates excerpts before merging signals. Context errors recursively split the failed segment, with a lower bound that produces a visible error rather than dropping content. Daily and monthly pairwise combination reduces intermediates with a bounded number of rounds; weekly composition is one final call over the compact merged packet.

On iOS 26.4 and later, the provider counts prompt, instruction and generated-schema tokens, reserves 1,200 tokens for output/framework overhead, and compares the total with `model.contextSize`. Earlier supported runtimes rely on segmentation and adaptive handling of the framework's context error. Each request caps generated response tokens at 650. Apple's context guidance explains that prompts, instructions, schemas and responses share the session budget and recommends processing smaller pieces separately. [Apple: managing context](https://developer.apple.com/documentation/foundationmodels/managing-the-context-window)

Analysis begins from successfully saved entries after editor completion, when a day opens, or when the app resumes with queued changes. Editor keystrokes and timeline color reads do not trigger inference. The editor's navy magnifying-glass control is the explicit exception: when pressed, it submits the draft exactly as displayed, then shows one grounded clarity note and probing question below the writing. This output is transient, is never inserted into the entry or persisted as analysis, and is canceled and removed when the draft changes or the editor closes. Its navy sextant requests another interpretation of the same visible draft. Opening a period reflection requests generation or reuses its cache. Every displayed daily, weekly and monthly output has the same accessible navy sextant button, which explicitly bypasses the selected result's valid cache and requests a new on-device interpretation. The previous stored result remains visible during generation or failure; the replacement still passes the committed-source fingerprint check and saves through the same isolated derived transaction. Refreshing never removes a separate emotion correction. The service maintains task identities so a duplicate request awaits ongoing work, including a month and an independently opened clipped week sharing the same period. App inactivity and entry editing cancel active service tasks; cancellation is checked around inference and before a derived save. No guaranteed background execution is assumed. Tasks waiting for serialized inference may finish cancellation only after earlier work releases the slot.

## Emotion presentation and corrections

The taxonomy is joy, peace, sadness, anger, fear, loneliness, love and mixed/uncertain. A fixed palette maps these values to gold, sage, muted blue, terracotta, dusty purple, gray-brown, rose and neutral. The new outlined day indicator uses this palette; decorative `Line` remains opaque `#323575`, journal markers remain gray and text/control tint remains Ink.

The daily reflection presents “Day summary” before an optional “Notable emotions” list. The list deduplicates primary and secondary suggestions and appears only for specific supported emotions or a user's explicit correction. The correction menu remains available even when the model reports no notable emotion. The selected correction takes precedence over an AI primary emotion. Choosing “Use AI suggestion” removes only the correction. A stale AI result remains labeled as earlier analysis, and stale AI emotion suggestions do not color the timeline. Timeline accessibility includes the emotion in text; color alone is not the meaning. Cached stored values render the indicators without another model request. At the two largest accessibility sizes, the day header uses native icons with complete accessible names and 44-point targets; its full date uses an uncapped scalable caption. Reflection content and native metadata controls remain scrollable.

## Privacy and verification limits

### Finn and Sophie fictional demo

The Debug-only `--seed-finn-sophie-demo` launch option activates a separate persistent `BearingsDemos/FinnSophie/FinnSophie.store`; it never replaces the normal `ReCollect/Journal.store`. The fixture contains twelve invented entries dated October 4–10, 2026 and deliberately leaves Sunday, October 11 empty. Its writing progresses from brief, vague notes to a fuller account of Finn's repeated impulse to instruct or correct Sophie when she describes pain.

The fixture also stores one prepared weekly reflection for the completed Sunday–Saturday period. `ReflectionContent.isPreparedDemo` makes the interface label that record as prepared fictional output. Sunday presents its summary and practical suggestion directly above the day branches, with the full reflection and refresh available from the same card. The ordinary refresh control bypasses the cache and replaces it through the same on-device generation and isolated-save path as any other reflection. The prepared record uses the current analysis version and exact current fingerprint. Daily analyses are legitimate new fingerprint inputs; if they make the still-prepared fixture stale, the next demo-store launch re-saves that same authored content against the current local inputs. A genuine refreshed model result has no prepared-demo marker and is never replaced by this repair. Journal edits keep their normal invalidation behavior. A later home-screen launch keeps using the separate demo store after activation; `--leave-finn-sophie-demo` returns Debug builds to the normal journal, and `--reset-finn-sophie-demo` resets only the demo directory when paired with the seed option.

The implementation has no network client, cloud AI provider, analytics SDK, CloudKit store or journal export path. Journals, corrections and generated results stay in the local SwiftData store. Provider/framework error payloads and transcripts are neither logged nor shown; unknown errors receive content-free messages. Synthetic UI and unit fixtures contain invented journal writing.

The directory and SQLite store/companions retain native iOS `completeUntilFirstUserAuthentication` protection. This supports use after the first unlock; it is not a claim that the store becomes inaccessible whenever the screen locks. Local persistence is separate from a user's OS-managed device backup: app data can be included in device backups according to system settings. Bearings does not implement cloud sync or send journal content for inference. Backup exclusion, encryption beyond platform protection and synchronization policy require a separate decision.

Ordinary tests inject deterministic intelligence and need no real model. A hosted physical-iPhone smoke test now verifies that the ready system model can complete Emotional Zoom, daily analysis, the staged weekly flow, monthly reflection, local persistence and cache reuse with synthetic writing. That structural pass does not establish reflection quality, semantic emotional accuracy, behavior across varied journals, energy/latency, locked-device behavior or disconnected execution.
